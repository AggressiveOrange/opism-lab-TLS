# Лабораторна робота 2. TLS та сертифікати

Методичні вказівки

## Мета роботи

Спостерегти рукостискання TLS на рівні записів, отримати сертифікат від центру сертифікації за протоколом ACME і встановити його на власний сервер, діагностувати несправності сертифікатів за виводом інструментів, виміряти, скільки часу коштує встановлення нового з'єднання HTTPS.

Робота спирається на матеріал теми 5. Протокол HTTP (тема 3) і DNS (тема 4) використовуються як відомі.

## Що здається

Звіт оформлюється в публічному репозиторії GitHub: файл `лб2-TLS-бланк.md` копіюється в репозиторій під назвою `README.md` і заповнюється. Вивід команд вставляється текстом у блоки коду, а не знімками екрана. Порожні поля не допускаються: якщо щось не вдалося, слід записати, що саме і на якому кроці.

Виводи вносяться у звіт у тому вигляді, в якому їх отримано. Скорочувати вивід можна лише там, де це прямо дозволено, і пропуски позначаються `…`.

Використання інструментів штучного інтелекту допускається за тих самих умов, що й у роботі з DNS: результати вимірювань отримуються самостійно, кожне звернення, що вплинуло на звіт, заноситься в декларацію з дослівним промптом.

Оцінка виставляється після захисту.

## Стенд

Стенд побудований так само, як стенд роботи з DNS: кожна роль працює в окремому контейнері Docker, усі контейнери з'єднані однією мережею `10.53.0.0/16`. Склад стенда:

| Вузол | Адреса | Призначення |
|---|---|---|
| root, TLD | `10.53.0.2`, `10.53.0.3` | ієрархія DNS, як у роботі 1 |
| resolver-a | `10.53.0.53` | рекурсивний резолвер |
| ca | `10.53.0.10` (`ca.lab`) | центр сертифікації з протоколом ACME (Pebble) |
| web | `10.53.0.80` | віддалений сервер HTTPS і сервери з несправностями |
| ваш контейнер | `10.53.1.N` | ваш сервер DNS, ваш сервер nginx і ваш термінал |

Зона `<id>.lab` вже заповнена всіма потрібними записами, редагувати її в цій роботі не потрібно.

На вихідному інтерфейсі вашого контейнера стенд додає штучну затримку. Її значення залежить від варіанта і в картці не наводиться: у завданні 5 його потрібно визначити вимірюванням.

На стенді працюють два незалежні центри сертифікації. Корінь стенда (`OPISM Stand Root CA`, файл `/lab/pki/stand-root.crt`, змінна `$STAND_CA`) підписав сертифікати віддаленого сервера і самого сервера ACME. Центр ACME (Pebble) видає сертифікати для вашого сервера. Pebble — тестовий центр сертифікації, який використовується для перевірки клієнтів ACME. Його кореневий і проміжний ключі створюються заново під час кожного запуску стенда.

> Після перезапуску стенда (зокрема після перезапуску codespace) корінь Pebble змінюється, і сертифікат, виданий раніше, більше не перевіряється. Якщо це сталося після завдання 3, сертифікат слід видати повторно (кроки 3.1, 3.3, 3.6) і зазначити це у звіті.

### Запуск у GitHub Codespaces

1. Відкрийте codespace у репозиторії з матеріалами курсу і перейдіть у каталог `tls-lab`.
2. Якщо запущено стенд роботи з DNS, його буде зупинено автоматично: обидва стенди використовують ті самі адреси.
3. Згенеруйте стенд для свого ідентифікатора (того самого, що в роботі з DNS) і запустіть його:

   ```
   python3 gen.py --student <id> --salt opism-2026
   ./up.sh
   ```

   Перший запуск збирає образ і триває кілька хвилин. Наприкінці `up.sh` виконує перевірку стенда. Усі рядки мають починатися з `OK`. Рядок `netem=NO` означає, що затримку не встановлено і завдання 5 виконати неможливо: зверніться до викладача.

4. Відкрийте картку варіанта `stand/cards/<id>.md`. У ній наведено логін, пароль і всі імена, потрібні для роботи.
5. Відкрийте вкладку PORTS, знайдіть порт 7001 і відкрийте його у браузері. Відкриється термінал вашого контейнера.

Усі команди нижче виконуються в цьому терміналі. Робочий каталог `/lab/work` зберігається між перезапусками, файли з виводами варто зберігати саме туди.

### Позначення

У командах використано позначення з картки варіанта:

| Позначення | Значення |
|---|---|
| `<id>` | ваш ідентифікатор |
| `<remote>` | ім'я віддаленого сервера, наприклад `edge.<id>.lab` |
| `<alias>` | друге ім'я для вашого сертифіката, наприклад `blog.<id>.lab` |

## Завдання 1. HTTP і HTTPS у дампі трафіку

**1.1.** Запишіть дамп запиту HTTP до віддаленого сервера:

```
cd /lab/work
timeout 8 tcpdump -ni eth0 -A -s0 -l 'host 10.53.0.80 and tcp port 80' > t1-http.txt &
sleep 1; curl -s http://<remote>/; wait
grep -a -E 'GET /|Host:|server: web' t1-http.txt
```

`tcpdump` записує дамп у файл протягом 8 секунд, `curl` виконує запит у цей час, `grep` вибирає з дампу рядки запиту і відповіді.

**1.2.** Повторіть те саме для HTTPS:

```
timeout 8 tcpdump -ni eth0 -A -s0 -l 'host 10.53.0.80 and tcp port 443' > t1-https.txt &
sleep 1; curl -s --cacert $STAND_CA https://<remote>/; wait
grep -a -c -E 'GET /|server: web' t1-https.txt
grep -a -o '<remote>' t1-https.txt | wc -l
```

Ключ `--cacert` вказує `curl`, якому кореневому сертифікату довіряти.

**1.3.** Порівняйте тіла двох відповідей сервера і дайте відповіді на питання бланка.

## Завдання 2. Рукостискання по записах

**2.1.** Отримайте послідовність записів TLS 1.3:

```
openssl s_client -connect <remote>:443 -servername <remote> -alpn h2,http/1.1 \
  -CAfile $STAND_CA -trace </dev/null > t2-13.txt 2>&1
grep -a -E '^(Sent|Received) Record|Content Type|^    [A-Z][A-Za-z]+, Length' t2-13.txt
grep -a -E '^(ALPN|New,)|Verify return' t2-13.txt
```

Ключ `-servername` задає SNI, ключ `-alpn` — перелік прикладних протоколів, які пропонує клієнт, ключ `-trace` виводить кожен надісланий і отриманий запис.

**2.2.** Виконайте ту саму команду з ключем `-tls1_2` і збережіть вивід у `t2-12.txt`.

**2.3.** Знайдіть у `t2-13.txt` розширення SNI:

```
grep -a -A3 'extension_type=server_name' t2-13.txt | head -4
```

**2.4.** Перевірте, чи видно сертифікат сервера в дампі трафіку. Для цього в обох версіях протоколу шукається ім'я проміжного центру, яке міститься в сертифікаті:

```
for v in 1.3 1.2; do
  timeout 6 tcpdump -ni eth0 -A -s0 -l 'host 10.53.0.80 and tcp port 443' > t2-dump-$v.txt &
  sleep 1; curl -s -o /dev/null --tlsv1.2 --tls-max $v --cacert $STAND_CA https://<remote>/; wait
  echo "TLS $v: $(grep -a -c 'OPISM Stand Intermediate' t2-dump-$v.txt)"
done
```

Ключі `--tlsv1.2 --tls-max X` обмежують версію протоколу знизу і зверху.

**2.5.** Заповніть таблиці бланка за виводами 2.1–2.4.

## Завдання 3. Сертифікат для власного сервера

Ваш контейнер має готовий сервер nginx. Його конфігурація (`/lab/nginx.conf`) вже налаштована: на порту 80 сервер відповідає на перевірки ACME, на порту 443 обслуговує імена `www.<id>.lab` і `<alias>` з сертифікатом `/lab/tls/server.crt` і ключем `/lab/tls/server.key`. Поки сертифікат не встановлено, там лежить тимчасовий самопідписаний сертифікат. Змінювати конфігурацію nginx не потрібно.

**3.1.** Збережіть поточний корінь центру ACME і виведіть його параметри:

```
acme-root
openssl x509 -in /lab/tls/acme-root.crt -noout -subject -dates
```

**3.2.** Переконайтеся, що з тимчасовим сертифікатом сервер не проходить перевірку:

```
curl -sS --cacert /lab/tls/acme-root.crt https://www.<id>.lab/
```

**3.3.** Отримайте сертифікат за протоколом ACME. Клієнт ACME `lego` створює обліковий запис у центрі сертифікації, замовляє сертифікат для двох імен, розміщує на вашому сервері файли перевірки HTTP-01 і після успішної перевірки отримує сертифікат:

```
lego --server $ACME_DIR --email admin@<id>.lab --accept-tos --path /lab/work/lego \
  --http --http.webroot /var/www/acme \
  --domains www.<id>.lab --domains <alias> run --no-bundle
grep acme-challenge /var/log/nginx/access.log
```

Ключ `--no-bundle` зберігає сертифікат сервера і сертифікат видавця в окремих файлах. Результат знаходиться в каталозі `/lab/work/lego/certificates/`.

**3.4.** Виведіть параметри отриманих сертифікатів:

```
cd /lab/work/lego/certificates
openssl x509 -in www.<id>.lab.crt -noout -subject -issuer -dates -serial -ext subjectAltName
openssl x509 -in www.<id>.lab.issuer.crt -noout -subject -issuer
```

**3.5.** Встановіть на сервер лише сертифікат сервера, без сертифіката видавця, і перевірте результат:

```
cp www.<id>.lab.crt /lab/tls/server.crt
cp www.<id>.lab.key /lab/tls/server.key
web-reload
curl -sS --cacert /lab/tls/acme-root.crt https://www.<id>.lab/
openssl s_client -connect www.<id>.lab:443 -servername www.<id>.lab -CAfile /lab/tls/acme-root.crt \
  </dev/null 2>/dev/null | sed -n '/^Certificate chain/,/^---/p;/^Verify return code/p'
```

**3.6.** Усуньте несправність, яку показав крок 3.5. Файл `/lab/tls/server.crt` має містити спочатку сертифікат сервера, потім сертифікат видавця:

```
cat www.<id>.lab.crt www.<id>.lab.issuer.crt > /lab/tls/server.crt
web-reload
```

Повторіть обидві перевірки кроку 3.5, а також запит `curl` до імені `<alias>`.

## Завдання 4. Діагностика несправностей

На сервері `web` працюють п'ять серверів `f1.<id>.lab` – `f5.<id>.lab`. Чотири з них мають несправні сертифікати, один справний. Набір несправностей і їх розподіл за іменами залежать від варіанта.

**4.1.** Виконайте для кожного сервера запит `curl` і виведіть ланцюжок, який сервер надсилає:

```
for i in 1 2 3 4 5; do
  n=f$i.<id>.lab; echo "=== $n"
  curl -sS --cacert $STAND_CA https://$n/ 2>&1 | head -1
  openssl s_client -connect $n:443 -servername $n -CAfile $STAND_CA </dev/null 2>/dev/null \
    | sed -n '/^Certificate chain/,/^---/p;/^Verify return code/p' | grep -v PKEY
done
```

**4.2.** Для кожного сервера визначте, яка з перевірок клієнта не пройшла, і вкажіть рядок виводу, який це доводить. Можливі несправності: прострочений сертифікат, ім'я відсутнє в SAN, самопідписаний сертифікат, сервер не надсилає проміжний сертифікат, сертифікат виданий центром, якому клієнт не довіряє.

**4.3.** Для кожного несправного сервера вкажіть, що має змінити його власник.

## Завдання 5. Ціна нового з'єднання

**5.1.** До вимірювання запишіть у бланк прогноз: скільки RTT займає кожен етап з'єднання для TLS 1.3, TLS 1.2 і для повторного використання з'єднання.

**5.2.** Виміряйте тривалість етапів для трьох нових з'єднань TLS 1.3 і трьох нових з'єднань TLS 1.2:

```
F='%{time_namelookup} %{time_connect} %{time_appconnect} %{time_starttransfer} %{time_total} %{http_version} %{num_connects}\n'
U=https://<remote>/
for i in 1 2 3; do curl -s -o /dev/null --cacert $STAND_CA -w "$F" $U; done
for i in 1 2 3; do curl -s -o /dev/null --tls-max 1.2 --cacert $STAND_CA -w "$F" $U; done
```

Кожне значення `time_*` — це час від початку запиту до завершення етапу, у секундах: `time_namelookup` — пошук імені, `time_connect` — встановлення з'єднання TCP, `time_appconnect` — завершення рукостискання TLS, `time_starttransfer` — отримання першого байта відповіді, `time_total` — завершення запиту. `num_connects` — кількість нових з'єднань, встановлених для запиту.

**5.3.** Виміряйте ті самі етапи для трьох запитів, виконаних однією командою. `curl` у такому разі використовує одне з'єднання для всіх трьох запитів:

```
curl -s --cacert $STAND_CA -w "$F" -o /dev/null $U -o /dev/null $U -o /dev/null $U
```

**5.4.** Визначте RTT і порівняйте результати з прогнозом.

## Висновки і декларація

Розділи «Висновки» і «Декларація використання ШІ» заповнюються так само, як у роботі з DNS. У висновках слід вказати результат, який не збігся з очікуванням, і питання, на яке не вдалося знайти відповідь, з посиланням на конкретний рядок виводу.
